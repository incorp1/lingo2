
# Правила точечных правок — Lingo Cards


Основание: исходники архива **v3.18.34**. Это инструкция модели, а не предложение переписать приложение. Если текущий код отличается от карты, верить коду и обновить только затронутую часть карты.


## 1. Как начать и не тратить лишние токены


1. Прочитай этот файл. Сформулируй запрошенное изменение одним предложением.
2. В `PROJECT_MAP.md` прочитай только раздел **«1. Куда идти по задаче»**. Выбери строку задачи.
3. Найди указанный символ/DOM-id в выбранном файле. Прочитай целиком нужную функцию и её непосредственные зависимости, а не весь проект. Для CSS проверь совпадения селектора в остальных стилях и порядок подключения.
4. До редактирования перечисли: **что меняю; какие файлы; как проверю**. Для простой правки не требуется длинный план.
5. Сделай минимальный законченный патч. Обычно это 1–3 рабочих файла плюс действительно необходимые переводы, тесты и релизные метки. Это ориентир, не запрет на обязательные связанные изменения.
6. Проверь патч и результат. Заверши после выполнения запроса; не добавляй улучшения «заодно».


**Расширять чтение только по причине:** неизвестный вызываемый символ, непонятный формат данных, конфликт стилей, падение теста или затронутый контракт. Один поиск по всему проекту допустим для неизвестного символа; дальше сужай область.


**Не читать по умолчанию:** `app-original.html`, все тесты подряд, все переводы целиком, lock-файлы, весь `storage.js`, весь `index.html`. `app-original.html` не подключён рабочей страницей или Service Worker; не считать его актуальной реализацией и не синхронизировать с ним изменения.


## 2. Что это за приложение


- Статическое PWA: обычные HTML/CSS/JavaScript. Нет React, сборщика, серверного приложения или ES-модулей.
- Рабочая страница — `index.html`. Файлы подключаются обычными `<script src>` в определённом порядке. Общие `let`/`const` не обязательно являются свойствами `window`.
- Постоянные данные — IndexedDB через `LCStorage`; `state` — состояние в памяти; `session` — текущая учебная сессия. Часть незавершённого обучения сохраняется отдельно в `state.studyCycles`.
- Для точечной правки **не устанавливай новый шаблон, фреймворк, backend и не меняй порядок скриптов**.
- У `package.json` есть только команда `test`. Не придумывай команды `build`, `lint` или `dev`.


## 3. Обязательные ограничения


### Данные


- Не менять имена БД/хранилищ, `STORAGE_KEY`, ID сущностей, формат копий и миграции без прямой необходимости.
- После изменения существующей карточки нужен `markCardDirty(card)`, колоды — `markDeckDirty(deck)`, настроек — `markSettingsDirty()`, общей метаинформации — `markMetaDirty()`.
- Для создания/переноса/удаления используй существующие помощники `createCard`, `createDeck`, `moveCardToDeck`, `removeCard`, `removeDeck` и соответствующие массовые функции: они поддерживают индексы и dirty-флаги. Одного изменения массива недостаточно.
- `save()` ставит изменения на сохранение; **`await save()` не подтверждает запись**. Для подтверждения используется `await saveAndFlush()`. Сохраняй существующие rollback-пути, проверки результата `mutateAndFlush` и обработку ошибок.
- Не показывай успех и не переключай карточку до подтверждения записи там, где это уже гарантируется кодом.
- Импорт/сброс/восстановление должны сохранять snapshot/revision/recovery-защиту. Никогда не «чинить» проблему очисткой пользовательской БД.
- Новое сохраняемое поле проверь по всей цепочке: создание → нормализация загрузки → dirty/save → перезагрузка → экспорт/импорт. Санитайзеры `backup.js` перечисляют разрешённые поля; новое поле иначе может исчезнуть из копии.


### Интерфейс и совместимость


- Не переименовывай DOM-id, классы, `data-*`, функции и глобальные переменные без проверки всех ссылок.
- Не дублируй обработчики и объявления. Проверяй, не привязана ли кнопка в `bindEvents()` или профильном `bind...()`.
- Для текста используй `t()` / существующие `data-i18n-*`; новые ключи добавляй в `i18n/ru.js`, `i18n/uk.js`, `i18n/en.js`, сохраняя переменные вида `{name}`.
- Для CSS меняй существующее правило-владелец, учитывая каскад. Не добавляй бесконечные переопределения в конец файла и не применяй глобальный селектор ради одного экрана.
- Сохраняй поддержку Safari/iOS 15: полифиллы в `theme-init.js`, fallback для новых CSS/API, touch-ветки выделения, `visualViewport`, safe-area, управление фокусом и reduced-motion. Проверка в desktop-браузере не равна проверке iPhone.
- Динамический пользовательский текст выводи через `textContent` либо существующее экранирование; не вставляй сырой HTML.


### AI и секреты


- Запросы идут из браузера через `ai.js`; UI/отмена — в `js/ui.js` и `js/ai-practice.js`. Сохраняй таймауты, отмену, проверку актуальности ответа и обработку лимитов.
- Не выводи ключи в ответ, логи, фикстуры или документацию. Полная резервная копия сейчас **включает AI-ключ**; её нельзя прикладывать к публичному отчёту.
- При новом провайдере проверь не только запрос, но и нормализацию, санитайзеры копий, интерфейс и CSP `_headers`. Не добавляй провайдера, если пользователь этого не просил.


## 4. Проверка и выпуск


- Запусти профильный тест из карты: `node --test tests/ИМЯ.test.js` (подставь реальное имя). Для нескольких тестов перечисли пути через пробел.
- Перед выдачей **изменённого приложения** выполни весь набор: `npm test`. Если зависимости ещё не установлены — `npm ci` с имеющимся `package-lock.json`. Не обновляй зависимости без необходимости.
- Для CSS/жестов/клавиатуры проверь затронутый экран вручную. Для сохранения — перезагрузку страницы; для PWA — повторный запуск без сети после онлайн-загрузки.
- Часть тестов проверяет исходный текст регулярными выражениями. Не удаляй проверки ради зелёного результата: отличай реальную регрессию от законного изменения контракта.
- Перед публикацией **изменённых ресурсов приложения** выполни раздел **«6. Выпуск PWA»** карты. Одна версия в `package.json` не обновляет кэш iPhone.
- Если изменена только документация, не повышай версию, не меняй кэш и не добавляй Markdown в `APP_SHELL`.
- При наличии Git проверь `git diff --check` и итоговый diff. Без Git сравни изменённые файлы с исходным архивом. Не форматируй весь файл ради нескольких строк.
- Если проверку не удалось выполнить, прямо укажи это. Не заявляй, что iPhone, AI API или сохранность данных проверены, без фактической проверки.

- Не проверено / риск: только если есть.
